Creacional

Factory Method

Define una interfaz para crear un objeto, pero deja que las subclases decidan qué clase instanciar.

Analogía principal

Una cadena de pizzerías define cómo se pide una pizza, pero cada sucursal decide qué pizza concreta hacer. El cliente pide "una napolitana" sin saber cómo se fabrica.

Ejemplos del día a día

🖨️
Driver de impresora
Tu PC manda "imprimir documento". No sabe si es HP, Epson o Canon. Cada driver (subclase) implementa el método imprimir() a su manera.
Pizzeria = tu PC · Pizza = documento · Subclase = cada driver
🎮
Spawn de enemigos
Un juego tiene un método SpawnEnemigo(). Cada nivel (subclase) decide qué enemigo concreto crear: zombie, esqueleto o dragón, según la dificultad.
Nivel = subclase · Enemigo = Pizza · SpawnEnemigo = CrearPizza
🚗
Concesionaria de autos
Una empresa pide "crear vehículo". La concesionaria Toyota crea un Corolla, la BMW crea un Serie 3. El cliente habla con "Concesionaria", nunca con la marca directamente.
Concesionaria = Pizzeria abstracta · Auto = Pizza abstracta

Estructura

  «abstract» Pizzeria
  └── CrearPizza(tipo)   ← Factory Method abstracto
       │
       ├──▶ PizzeriaArgentina  ──▶ PizzaCancha("Argentina")
       └──▶ PizzeriaItaliana   ──▶ PizzaNapolitana("Italia")

  «abstract» Pizza
  ├── PizzaCancha
  └── PizzaNapolitana

Código paso a paso

1
Pizza — clase base abstract. Tiene _descripcion y _origen. Su método Render() imprime ambos. No se puede instanciar directamente.
Pizza.cs
public abstract class Pizza
{
    protected string _descripcion;
    protected string _origen;

    public void Render()
        => Console.WriteLine($"Pizza de {_descripcion} hecha en {_origen}");
}
2
PizzaCancha / PizzaNapolitana — subclases concretas. Solo asignan _descripcion y reciben _origen del constructor. Heredan Render() gratis.
PizzaCancha.cs
public class PizzaCancha : Pizza
{
    public PizzaCancha(string origen)
    {
        _descripcion = "Pizza de cancha";
        _origen = origen;  // quien la crea decide el origen
    }
}
3
Pizzeria — contiene el Factory Method abstracto. Declara CrearPizza(tipo) sin cuerpo: "sé que hay que crear una pizza, pero no sé cuál".
Pizzeria.cs
public abstract class Pizzeria
{
    public abstract Pizza CrearPizza(string tipo);  ← Factory Method
}
4
PizzeriaArgentina / PizzeriaItaliana — implementan el método con override. Cada una decide qué objeto Pizza concreto crear.
PizzeriaArgentina.cs
public class PizzeriaArgentina : Pizzeria
{
    public override Pizza CrearPizza(string tipo)
    {
        if (tipo == "cancha")  return new PizzaCancha("Argentina");
        if (tipo == "napo")    return new PizzaNapolitana("Argentina");
        return null;
    }
}
5
Program.cs — el cliente habla solo con Pizzeria y Pizza. Cambiar de pizzería no toca el código que pide pizzas.
Program.cs
Pizzeria pizzeria = new PizzeriaArgentina();
Pizza pizza = pizzeria.CrearPizza("napo");
pizza.Render();  // Pizza de Pizza napolitana! hecha en Argentina

pizzeria = new PizzeriaItaliana();  // solo cambiamos la fábrica
pizza = pizzeria.CrearPizza("cancha");
pizza.Render();  // Pizza de Pizza de cancha hecha en Italia
Clave: el cliente nunca instancia PizzaCancha ni PizzeriaArgentina directamente. Siempre habla con las abstracciones. Agregar nueva pizzería o tipo de pizza no rompe al cliente.

Creacional

Abstract Factory

Proporciona una interfaz para crear familias de objetos relacionados sin especificar sus clases concretas.

Analogía principal

Cada pizzería no solo hace pizzas sino también empanadas. La PizzeriaArgentina siempre da pizza de cancha + empanada de carne (su "familia"). No podés mezclar pizza italiana con empanada de ceviche.

Ejemplos del día a día

📱
Apple vs Android
Apple fabrica iPhone + AirPods + Apple Watch (familia consistente). Google fabrica Pixel + Pixel Buds + Pixel Watch. No mezclás AirPods con Android: son familias distintas.
Marca = fábrica abstracta · Dispositivos = familia de productos
🖥️
PC Gamer vs PC Trabajo
Una "fábrica Gamer" crea placa de video potente + monitor 144hz + teclado mecánico. Una "fábrica Trabajo" crea monitor 60hz + teclado básico. Familia coherente por fábrica.
Tipo de PC = fábrica · Componentes = familia de productos
🍔
McDonald's vs Burger King
Cada cadena tiene su Hamburguesa + Papas + Bebida propias. No pedís una BigMac con las papas de Burger King. Cada fábrica garantiza consistencia dentro de su familia.
Cadena = fábrica · Combo = familia de productos

Factory Method vs Abstract Factory

Factory Method
Crea un solo tipo de objeto
CrearPizza(tipo) → un Pizza
Abstract Factory
Crea una familia entera
CrearPizza() + CrearEmpanada()

Estructura

  «abstract» Pizzeria
  ├── CrearPizza()       ← producto 1
  └── CrearEmpanada()    ← producto 2 (familia)

  ├──▶ PizzeriaArgentina  →  PizzaCancha      + EmpanadaDeCarne
  ├──▶ PizzeriaItaliana   →  PizzaNapolitana  + EmpanadaCapresse
  └──▶ PizzeriaChina      →  PizzaSushi       + EmpanadaCeviche

Código paso a paso

1
Pizzeria (Abstract Factory) — ahora tiene dos métodos abstractos, uno por producto. Sin parámetros: la fábrica concreta ya sabe qué crear.
Pizzeria.cs
public abstract class Pizzeria
{
    public abstract Pizza    CrearPizza();     // sin parámetro
    public abstract Empanada CrearEmpanada();  // sin parámetro
}
2
Fábricas concretas — implementan ambos métodos y siempre retornan la familia consistente.
PizzeriaArgentina.cs / PizzeriaChina.cs
public class PizzeriaArgentina : Pizzeria
{
    public override Pizza    CrearPizza()     => new PizzaCancha();
    public override Empanada CrearEmpanada() => new EmpanadaDeCarne();
}
public class PizzeriaChina : Pizzeria
{
    public override Pizza    CrearPizza()     => new PizzaSushi();
    public override Empanada CrearEmpanada() => new EmpanadaCeviche();
}
3
Program.cs — el cliente solo cambia la fábrica y automáticamente recibe la familia correcta.
Program.cs
Pizzeria fabrica = new PizzeriaArgentina();
Pizza pizza = fabrica.CrearPizza();
Empanada emp = fabrica.CrearEmpanada();
Console.WriteLine($"Pizza: {pizza.Descripcion}, Empanada: {emp.Descripcion}");
// Pizza: Pizza de cancha, Empanada: Empanada de carne

fabrica = new PizzeriaChina();  // solo esto cambia
// Pizza: Pizza especial de sushi, Empanada: Empada de ceviche
Clave: garantiza que los productos sean siempre de la misma familia. Es imposible mezclar PizzaCancha con EmpanadaCeviche usando el patrón correctamente.

Estructural

Adapter

Permite que interfaces incompatibles trabajen juntas convirtiendo la interfaz de una clase en la que el cliente espera.

Analogía principal

Tu auto espera un motor con Arrancar(), Acelerar(). El motor eléctrico habla en Conectar(), Mover(). El Adapter es el "traductor" en el medio.

Ejemplos del día a día

🔌
Cable HDMI a VGA
Tu notebook tiene salida HDMI. El proyector del aula tiene entrada VGA. El cable adaptador convierte la señal sin que vos ni el proyector tengan que cambiar.
Notebook = cliente · Proyector = clase incompatible · Cable = Adapter
🌐
Traductor simultáneo
El presidente japonés habla en japonés (interfaz A). La audiencia argentina espera español (interfaz B). El intérprete (Adapter) traduce en tiempo real sin que ninguno cambie cómo habla.
Audiencia = cliente · Japonés = clase incompatible · Intérprete = Adapter
💳
Gateway de pagos
Tu app llama a ProcesarPago(monto). MercadoPago tiene IniciarTransaccion(), PayPal tiene SendMoney(). Un Adapter por cada gateway traduce al mismo contrato.
Tu app = cliente · Gateways = clases incompatibles · Adapters = traductores

Estructura

  «abstract» Motor               ← interfaz que el cliente usa
  ├── Arrancar() / Acelerar()
  ├── Detener() / CargarCombustible()

  ├──▶ MotorNaftero           ← implementa directamente
  ├──▶ MotorDiesel            ← implementa directamente
  └──▶ MotorElectricoAdapter   ← el Adapter
         └── MotorElectrico      ← clase incompatible
              ├── Conectar() / Activar()
              └── Mover() / Parar() / Enchufar()

Código paso a paso

1
Motor — contrato abstracto que el cliente conoce. Cuatro métodos. El cliente solo habla con esta abstracción.
Motor.cs
public abstract class Motor
{
    public abstract void Arrancar();
    public abstract void Acelerar();
    public abstract void Detener();
    public abstract void CargarCombustible();
}
2
MotorElectrico — clase existente que no hereda de Motor y tiene métodos con nombres distintos. No podés modificarla.
MotorElectrico.cs — clase incompatible
public class MotorElectrico    // NO hereda de Motor
{
    public void Conectar()    { ... }   // ≈ Arrancar parte 1
    public void Activar()     { ... }   // ≈ Arrancar parte 2
    public void Mover()       { ... }   // ≈ Acelerar
    public void Parar()       { ... }   // ≈ parte de Detener
    public void Desactivar()  { ... }   // ≈ parte de Detener
    public void Enchufar()    { ... }   // ≈ CargarCombustible
}
3
MotorElectricoAdapter — hereda de Motor (contrato del cliente) y contiene un MotorElectrico. Traduce cada llamada.
MotorElectricoAdapter.cs
public class MotorElectricoAdapter : Motor
{
    MotorElectrico motorElectrico = new MotorElectrico();

    public override void Arrancar()
    {
        motorElectrico.Conectar();   // 1 llamada se convierte en 2
        motorElectrico.Activar();
    }
    public override void Acelerar()         => motorElectrico.Mover();
    public override void Detener()
    {
        motorElectrico.Desactivar();
        motorElectrico.Parar();
    }
    public override void CargarCombustible() => motorElectrico.Enchufar();
}
4
Program.cs — el cliente llama los mismos 4 métodos en los tres motores. No sabe que internamente el eléctrico hace llamadas distintas.
Program.cs
Motor m3 = new MotorElectricoAdapter();
m3.Arrancar();  // → Conectar() + Activar()
m3.Acelerar();  // → Mover()
m3.Detener();   // → Desactivar() + Parar()
Clave: el cliente nunca sabe que existe MotorElectrico. El Adapter absorbe la incompatibilidad. Para agregar un motor de hidrógeno, solo creás MotorHidrogenoAdapter sin tocar nada más.

Estructural

Decorator

Agrega responsabilidades a un objeto dinámicamente. Alternativa flexible a la herencia para extender funcionalidad.

Analogía principal

Café solo ($10) + leche (+$2) + azúcar (+$0.50) + crema (+$4). Cada topping envuelve la bebida anterior sumando al costo y la descripción. No creás CafeConLecheYCremaYAzucar.

Ejemplos del día a día

🎵
Suscripciones Spotify
Free (base) → Premium (+sin ads, +calidad) → Family Premium (+6 cuentas) → Duo (+2 premium). Cada nivel decora al anterior sin reescribir la clase base.
Free = bebida base · Premium = Decorator · Funciones = Costo + Descripcion
🚗
Accesorios de auto
Auto base ($20k) + GPS (+$2k) + sistema de sonido (+$3k) + techo solar (+$4k). Cada accesorio envuelve el auto anterior sin cambiar el modelo base.
Auto base = BebidaComponent · Accesorio = AgregadoDecorator
📸
Filtros de Instagram
Foto original → filtro Clarendon → sticker → texto. Cada elemento envuelve al anterior y agrega su efecto. La foto base no cambia.
Foto = Component · Filtro/Sticker = Decorador · Render = Descripcion

Estructura

  «abstract» BebidaComponent       ← interfaz común
  ├── Costo: double
  └── Descripcion: string

  Bases (Component concreto):          Decoradores:
  ├──▶ CafeSolo         $10         «abstract» AgregadoDecorator : BebidaComponent
  ├──▶ CafeExpresso      $12         └── _bebida: BebidaComponent
  ├──▶ CafeDescafeinado  $15
  └──▶ TeTradicional     $8          ├──▶ Leche +$2 / Azucar +$0.50
                                       ├──▶ Crema +$4 / Canela +$1.75
                                       └──▶ Edulcorante +$1

Código paso a paso

1
BebidaComponent — interfaz común para bebidas y decoradores. Al tener el mismo tipo, podés pasar un decorador donde se espera una bebida.
BebidaComponent.cs
public abstract class BebidaComponent
{
    public abstract double Costo { get; }
    public abstract string Descripcion { get; }
}
2
AgregadoDecorator — hereda de BebidaComponent Y tiene una BebidaComponent adentro (_bebida). Esto habilita el apilado infinito.
AgregadoDecorator.cs — el corazón del patrón
public abstract class AgregadoDecorator : BebidaComponent
{
    protected BebidaComponent _bebida;  // envuelve a otra bebida

    public AgregadoDecorator(BebidaComponent bebida) { _bebida = bebida; }
}
3
Decoradores concretos — cada uno suma su precio y agrega su nombre. El patrón siempre es _bebida.Costo + miCosto.
Leche.cs / Crema.cs
public class Leche : AgregadoDecorator
{
    public Leche(BebidaComponent b) : base(b) { }
    public override double Costo       => _bebida.Costo + 2;
    public override string Descripcion => $"{_bebida.Descripcion}, Leche";
}
public class Crema : AgregadoDecorator
{
    public Crema(BebidaComponent b) : base(b) { }
    public override double Costo       => _bebida.Costo + 4;
    public override string Descripcion => $"{_bebida.Descripcion}, Crema";
}
4
Program.cs — el apilado en acción. Cada línea envuelve la anterior. La variable siempre es de tipo BebidaComponent.
Program.cs
BebidaComponent cafe = new CafeDescafeinado(); // $15
cafe = new Crema(cafe);                          // +$4 → $19
cafe = new Edulcorante(cafe);                    // +$1 → $20
cafe = new Canela(cafe);                         // +$1.75 → $21.75

// Café descafeinado, Crema, Edulcorante, Canela - $21.75
Clave: con 4 decoradores y 4 bebidas base generás miles de combinaciones sin explotar en herencia. Sin Decorator necesitarías una clase por cada combinación posible.
Consola de código — Decorator (5 desafíos)

Conductual

Memento

Captura y externaliza el estado interno de un objeto para que pueda restaurarse luego, sin violar el encapsulamiento.

Analogía principal

Es el Ctrl+Z de tu editor. Cada vez que modificás, el editor guarda un snapshot. Al deshacer, restaura el anterior. El historial = CareTaker, cada snapshot = Memento, el documento = Originator.

Ejemplos del día a día

💾
Git commits
Cada git commit es un Memento del código. git checkout abc123 es restoreToMemento. El repositorio es el CareTaker: guarda todos los commits sin entender su contenido.
Tu código = Originator · Commit = Memento · Repo = CareTaker
🎮
Puntos de guardado
En un videojuego, llegás a un checkpoint y guardás. Si morís, cargás el guardado. El juego no sabe qué hay en el archivo de guardado, solo lo restaura.
Personaje = Originator · Archivo guardado = Memento · Lista de saves = CareTaker
📝
Historial de Photoshop
Cada acción en Photoshop (aplicar filtro, cortar, pintar) guarda un estado en el panel "Historial". Podés volver a cualquier punto anterior de la edición.
Imagen editada = Originator · Estado guardado = Memento · Panel historial = CareTaker

Los tres roles

Originator
Persona

El objeto cuyo estado queremos guardar y restaurar
Memento
Memento

Snapshot del estado. Solo el Originator sabe qué hay adentro
CareTaker
CareTaker

Guarda los Mementos sin examinar su contenido

Código paso a paso

1
Memento — el snapshot. Guarda _estado como readonly (solo getter). Una vez creado, nadie puede modificarlo.
Memento.cs
public class Memento
{
    private string _estado;
    public Memento(string estado) { _estado = estado; }
    public string Estado => _estado;  // solo lectura
}
2
CareTaker — historial de snapshots. Solo tiene Add() y GetMemento(índice). Nunca interpreta el contenido.
CareTaker.cs
public class CareTaker
{
    private List<Memento> _mementos = new List<Memento>();
    public void    Add(Memento m)       => _mementos.Add(m);
    public Memento GetMemento(int i)   => _mementos[i];
}
3
Persona (Originator) — saveToMemento() crea un snapshot del estado actual. restoreToMemento() lo aplica.
Persona.cs
public class Persona
{
    public string Nombre { get; set; }

    public Memento saveToMemento()
    {
        Console.WriteLine("Originator: Guardando memento para " + Nombre);
        return new Memento(Nombre);    // snapshot del estado actual
    }

    public void restoreToMemento(Memento m)
    {
        Nombre = m.Estado;              // restaura el estado
        Console.WriteLine("Originator: Recuperando memento  " + Nombre);
    }
}
4
Program.cs — guardar y restaurar estados en cualquier orden.
Program.cs
var p = new Persona();
var caretaker = new CareTaker();

p.Nombre = "Pepe";
caretaker.Add(p.saveToMemento());   // índice 0

p.Nombre = "Pepe1";
caretaker.Add(p.saveToMemento());   // índice 1

p.restoreToMemento(caretaker.GetMemento(0));  // vuelve a "Pepe"
p.restoreToMemento(caretaker.GetMemento(1));  // vuelve a "Pepe1"
Clave: CareTaker nunca lee el contenido de los Mementos. Son "cajas negras" para él. Solo Persona sabe cómo interpretar un Memento. Eso preserva el encapsulamiento.
